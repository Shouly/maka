# 企业服务端平台设计（草案）

- 状态：决定已全部定下（§0）；还需要业务方确认的问题见 §12
- 日期：2026-09-25
- 范围：为 Maka 桌面端新写一个组织级服务端。relx-copilot 只作设计参考，不复用代码，不迁移数据。

## 0. 决定

以下选择全部已定，按业界通行做法取舍。每项写明它问的是什么、定了什么、为什么。

| # | 它问的是什么 | 定了什么 | 为什么 |
|---|---|---|---|
| D1 | 服务端程序用哪种编程语言写 | TypeScript（运行在 Node 22 上） | Maka 本身就是 TypeScript。服务端和桌面端之间来回传的数据格式（请求、响应、事件）只需定义一份，两边直接共用，不会出现"服务端改了字段、桌面端没跟上"的问题；阶段 3 服务器上跑的共享 agent 本身就是 Maka 引擎，同一种语言才能直接复用 |
| D2 | 服务端装在哪里、依赖哪些云服务 | 不绑定任何云。以容器镜像 + Helm chart 交付，Docker Compose 用于试用；只依赖通用组件，密钥管理走接口（§3.1） | 能装在任何云或内网；RELX 装在 GCP 上只是其中一种部署 |
| D3 | 模型网关怎么实现 | 在平台服务里自己实现一个"薄"的透传网关：对 Maka 原样提供 Anthropic、OpenAI、Gemini 三种原生接口，背后通过上游适配器接到各家厂商（§5） | 网关必须和我们自己的登录、额度、策略、审计紧密结合；各家接口原样透传，才能保留 Claude 的 thinking、提示词缓存等能力；真正要写的只有鉴权、路由、流式转发、用量统计，以及 Bedrock、Vertex 这几个上游适配器，规模可控 |
| D4 | 员工怎么登录；同一个人用两种方式登录算不算同一个账号 | 先只接 Google 和 RELX SSO；邮箱唯一，同一个邮箱就是同一个人；身份源做成适配器，以后再扩展（§4.1） | 满足当前需要；relx 的漏洞不在按邮箱认人，而在邮箱由客户端提交、没有核实 |
| D5 | 管理员在哪里操作 | 服务端自带一个网页管理后台，阶段 1 就有：用户、模型与上游、额度、用量、审计日志；阶段 2 增加策略和技能目录（§3.2） | 企业 IT 习惯在浏览器里管理，不需要安装桌面端；管理后台和服务端一起部署、一起升级 |
| D6 | 网关要不要把员工和 AI 的对话原文保存下来 | 默认不存原文，只记"谁、什么时候、用了哪个模型、多少 token、花了多少"。确实需要时，管理员可以打开"保存对话内容"：同时要设保存期限，只有指定的合规人员能查看，查看行为本身也要记审计，并提前告知员工 | 原文可能包含客户资料、代码和个人信息，存下来既是隐私风险，也是数据泄露面。只记元数据已经够用于计费、额度和用量分析 |
| D7 | 群聊里的共享 agent 在服务器上执行命令、跑代码时，把它关在什么样的"隔离间"里 | 沙箱做成可替换的接口，默认用 E2B：每个线程一个 E2B 沙箱（Firecracker 微虚拟机，每个沙箱有自己的内核），里面预装并启动 Maka Runtime Host；线程空闲时暂停沙箱（文件和内存都保留），再有人 @ 时恢复；网络出口按频道设白名单。RELX 这套部署直接用 E2B 云（已确认可以接受数据进 E2B 云）。不能把数据交给 E2B 云的组织，用 E2B 的 BYOC（部署在自己的 AWS/GCP 账号里），或者换成自建的 Kubernetes + gVisor 实现（§8.6） | agent 会执行任意命令，一旦出错或被诱导执行恶意指令，也只能在自己的隔离间里折腾。E2B 已经具备这里需要的全部能力：微虚拟机级隔离、自定义镜像、暂停恢复、出口白名单，不用自己搭沙箱集群，阶段 3 也不再要求 Kubernetes；relx-copilot 团队也已经用熟了 |
| D8 | 群聊放在哪里 | 在 Maka 应用里新增 IM 功能：频道、私聊、线程、@提及、附件、未读和通知。agent 是 IM 里的成员，被 @ 就在线程里干活，类似 Claude Tag。消息、频道和实时推送由服务端负责（§8） | 人和 agent 的协作放在同一个应用里：对话、任务、产出、本机执行都在一处，不必在聊天工具和 Maka 之间来回切换 |
| D9 | 员工能不能在 Maka 里自己添加模型连接（用自己的 API key） | 能，保留现有功能。组织策略里有一个开关，管理员可以按需关闭，或只允许特定厂商 | 自带 key 对个人很方便，也便于试用新模型。代价是这部分调用不经过公司网关，所以不计入公司额度，也不进公司审计；需要严格数据管控的组织可以用策略关掉 |

## 1. 背景与目标

relx-copilot 的网页端和后端都不满足需求：

- **网页形态**：agent 碰不到员工电脑上的代码、文件、终端和本地应用，只能在云沙箱里工作；任务生命周期受浏览器拖累；系统集成做不深。
- **后端**：
  - 围绕"agent 在服务器上跑"建立，会话、推流、沙箱、额度汇总都绑在服务端 agent 循环上；
  - 身份层有根本问题：`/auth/sso/callback` 可凭邮箱冒充任何人；没有刷新和吊销；没有组织层级；
  - 第三方令牌看起来是明文存库；
  - Python 与 Maka 无法共享代码。

**目标**：Maka 是唯一的 agent 引擎。服务端只负责多人共享的状态和组织能力：身份、模型接入与额度、策略、目录、群聊，以及服务器上运行的共享 agent。

**非目标（第一版不做）**：会议转写、知识库、钉钉/NocoBase 等业务集成、网页版客户端、移动端（包括 IM 的手机端）、接入外部 IM（钉钉、飞书、Slack 等）、relx 数据迁移、群聊 agent 的"自动插话"、桌面端安装包的分发与自动更新。

## 2. 约束

- 用户规模：最多 500 人。
- 身份源只有两个：
  - **Google Workspace**：标准 OIDC。
  - **RELX 企业 SSO**：非标准 OAuth2。token 请求用 GET、参数放在 URL；userinfo 用 POST；成功码 `10000`；scope 以逗号分隔 `uid,name,email`。见 relx-copilot `backend/app/core/oauth.py`。
- 不迁移 relx 数据，两个系统并行，直到新系统可以替代。

规模带来的结论：单区域、单体服务、一个 Postgres 足够；不需要微服务。一套部署只服务一个组织（单租户），不做多租户。

以上是 RELX 这一套部署的条件。平台本身不绑定任何云和任何模型厂商（D2）。

## 3. 总体架构

```
员工电脑（每人一份）                      服务器（公司统一一份）
Maka 桌面端                              Platform API（单体，TypeScript，可多实例）
  · 本机 Runtime Host  ──HTTPS / WS──▶    ├─ 身份与组织
  · 本机执行 agent                         ├─ 模型与搜索网关 ──▶ 可配置的上游（Anthropic、Bedrock、
                                          │                    Vertex、OpenAI、Azure OpenAI、自部署模型）
                                          ├─ 策略与目录 ──▶ 对象存储（技能与插件包）
                                          ├─ IM：频道、消息、实时推送（阶段 3）
                                          ├─ 管理后台（网页）
                                          └─ Postgres、Redis
                                        共享 agent 沙箱（阶段 3，默认 E2B）
                                          └─ 每个线程一个沙箱，里面跑 Maka Runtime Host
```

- **服务端是独立部署的服务**，不打包进桌面安装包。源码放在 Maka 的 monorepo 里：新增 `apps/server`（服务）和 `packages/platform-protocol`（服务端与桌面端共用的接口定义），构建时单独打成镜像。全部是新增内容，不改上游文件。
- **API 层不跑 agent。** relx 把 agent 放在 API 进程里以 asyncio 任务运行，这里吸取教训：agent 在各自的沙箱里运行，平台服务只负责调度、转发和记录。
- **框架**：Fastify；数据库访问用 Kysely（类型安全的 SQL 查询构建器，不引入重量级 ORM）。
- **WebSocket**：负载均衡和托管平台普遍对长连接设有空闲或时长上限，客户端按"随时可能断开、断开后按 seq 补齐"设计。

### 3.1 不绑定任何云（D2）

每个外部依赖只用通用协议，或者隔着一层接口：

| 依赖 | 做法 | 可以对接的实现 |
|---|---|---|
| 数据库 | 只用标准 Postgres 功能，不用云厂商扩展 | 任何托管 Postgres（RDS、Cloud SQL、Azure Database），或自建 |
| 缓存与 pub/sub | Redis 协议；阶段 1、2 不需要，额度和限流先用 Postgres，阶段 3 的 IM 实时推送才引入 | 任何托管 Redis，或自建 |
| 对象存储 | 走存储接口，先实现 S3 协议 | AWS S3、MinIO、GCS（S3 兼容模式）；Azure Blob 另写一个实现 |
| 密钥管理 | 走密钥接口，信封加密 | AWS KMS、GCP KMS、Azure Key Vault、HashiCorp Vault；小规模安装可用本地主密钥 |
| 模型 | 网关内的上游适配器，见 §5 | Anthropic、Bedrock、Vertex、OpenAI、Azure OpenAI、任何 OpenAI 兼容的自部署模型 |
| 共享 agent 沙箱 | 走沙箱接口（D7） | E2B 云、E2B BYOC（AWS、GCP）、自建 Kubernetes + gVisor |
| 部署 | 容器镜像 + Helm chart；Docker Compose 用于试用 | 任何 Kubernetes（EKS、GKE、AKS、自建），或单机 Docker；平台服务本身不要求 Kubernetes |

### 3.2 管理后台（D5）

- 服务端自带的网页应用，和 API 同一个服务、同一个镜像。
- 只有组织管理员能进；登录方式和员工一样（Google / RELX SSO），用浏览器会话 cookie（HttpOnly、SameSite，并做 CSRF 防护），不用桌面端的令牌。
- 阶段 1：用户、模型与上游、额度、用量报表、审计日志、设备会话。
- 阶段 2：组织策略、技能与插件目录。
- 阶段 3：频道管理、每个频道的 agent 配置与授权、消息保留期限。
- 前端用 React + 与 Maka 相同的设计系统，作为 `apps/server` 里的一个单页应用，由服务端直接托管。

## 4. 身份与组织（阶段 1）

### 4.1 服务端作为授权服务器

服务端对 Maka 签发自己的令牌，上游对接两个身份源：

- **Google**：OIDC 授权码流程。要求 `email_verified`，并且 ID token 必须带 `hd`（Workspace 域名）：个人 Google 账号一律拒绝——服务端无法确认客户端是 Internal 类型，而员工用工作邮箱注册的个人账号在离职后依然有效。配置了域名白名单时，`hd` 还必须在白名单里。
- **RELX SSO**：只在服务端写一个专用适配器，把它的非标准流程吃掉，对外仍是标准流程。`state` 必须严格校验：relx 生成了 state 却从不检查。
- **账号身份（D4）**：邮箱唯一，同一邮箱就是同一个人。表结构是 `users.email` 唯一，外加 `identity_links(provider, subject) → user_id`。登录时先按 `(身份源, subject)` 找人，找不到再按邮箱找到同一个人并建立绑定；员工改了邮箱，账号也不会丢。按邮箱认人的三条前提：
  1. 邮箱只取自服务端向身份源拿到的用户信息，客户端提交的邮箱一律不认；
  2. 只认已验证的邮箱：Google 要求 `email_verified`；RELX SSO 返回的邮箱视为已验证（**待向 RELX IT 确认**）；
  3. 谁能登录由身份源决定：RELX SSO 本身就是公司目录；Google 用 Internal 类型的 OAuth 客户端，Google 只放行公司 Workspace 的账号。服务端另有一个可选的邮箱域名白名单（`MAKA_ALLOWED_EMAIL_DOMAINS`），默认不设；只有 Google 客户端是 External 类型（任何 Google 账号都能通过）时才需要配置。
- **RELX 这套部署的身份源**：复用 Y（relx-copilot）已注册的 Google OAuth 客户端和 RELX SSO 应用。每个身份源的回调地址可配置（`GOOGLE_REDIRECT_URI`、`RELX_SSO_REDIRECT_URI`，默认是 `<服务地址>/login/<身份源>/callback`），所以可以直接复用 Y 已经登记过的回调：本地开发时服务跑在 `localhost:3000`，回调用 Y 开发环境的 `/auth/google/callback` 和 `/auth/enterprise/callback`，不需要新登记。正式部署时，要么在两边登记新服务的回调地址，要么部署在 Y 已登记的地址下。两套系统共用同一个 secret，轮换时要一起改；Y 的 Google 客户端需要确认是 Internal 类型。
- **按邮箱绑定的边界**：按邮箱找到的账号如果已被停用，不建立新绑定；如果同一身份源下已经有另一个 subject 绑在这个账号上（例如邮箱被重新分配给新员工），拒绝登录（`identity_conflict`）并记审计，由管理员用 `users links` / `users unlink` 处理，避免新人继承旧人的角色和数据。
- **首次登录自动建号**：身份源放行的人第一次登录时自动创建账号，套用默认额度。管理员不需要提前导入名单。
- **扩展**：身份源实现为适配器接口（发起授权、换取身份、返回已验证的邮箱和 subject）。以后接 Azure AD、通用 OIDC、SAML，或整体换成身份代理（Keycloak、Zitadel 等），都只是新增一个适配器。

### 4.2 桌面端登录

按 RFC 8252（原生应用的 OAuth）：

1. Maka 用系统浏览器打开服务端登录页，带 PKCE 的 `code_challenge`，回调地址是 `http://127.0.0.1:<随机端口>`。
2. 用户在登录页选择 Google 或 RELX 并完成登录。
3. 服务端回调到本机回环地址；Maka 用 `code + code_verifier` 换取令牌。

浏览器完成页照 Claude 桌面端的样式：标志、"在 Maka 应用中完成登录"、一句说明和"打开 Maka"按钮。页面会自动跳转 `maka://open`（开发版 `maka-dev://open`），浏览器询问后把 Maka 切到前台；这个链接只负责聚焦窗口，不携带任何数据。macOS 只把协议交给在 Info.plist 里声明过它的应用：打包版由 electron-builder 的 `protocols` 声明，开发版只有 `MAKA_DEV_TCC=1` 生成的 Maka Dev.app 声明了 `maka-dev`。

桌面端强制登录时的界面照 Claude 首次启动：600×600 的小窗口，先是欢迎页（标志、"Maka *for* Mac"、"开始使用"），再是 Sign In（Google 在"OR"上方，RELX SSO 为主按钮）；浏览器登录期间只有被点的按钮转圈，没有其他提示，再点一次即重新开始。登录成功后窗口恢复为用户自己的大小，退出登录再缩回小窗口；小窗口的尺寸不写入 `window-state.json`。

如果某些电脑的安全软件拦截本机端口，改用自定义协议 `maka://` 回调作为备选。

命令行版（Maka CLI/TUI）的组织账号登录放到以后，届时用设备码流程（在浏览器里输入一个短码完成登录）。

### 4.3 令牌与离职

| 令牌 | 形式 | 有效期 | 说明 |
|---|---|---|---|
| access token | JWT（ES256） | 15 分钟 | 非对称签名，网关和沙箱里的引擎都可以本地验签 |
| refresh token | 不透明随机串，服务端只存哈希 | 使用中滚动续期，但距上次在身份源登录**最长 7 天** | 每次使用都轮换；发现旧令牌被复用就吊销整条链——例外是轮换后 60 秒内、它的继任令牌还没被用过：那是同一台设备没收到上次的应答在重试，发一个新的继任令牌并作废没送达的那个，而不是把人登出 |

"最长 7 天"是为了离职：第一版没有 SCIM（身份源通知"某人已离职"的标准协议）。如果 refresh token 可以无限滚动，离职员工只要天天在用，就永远不会被要求重新登录。设了上限，最迟 7 天必须回到 Google 或 RELX SSO 重新登录，而离职员工在那里已经登不上。需要立即生效时，管理员停用账号：服务端每次请求都会核对会话和账号状态，所以停用或吊销立刻生效，不必等 access token 过期。

每台设备一条会话记录，用户和管理员都能吊销。

Maka 本地存储：现在的 `packages/storage/src/credential-store.ts` 是权限 0600 的明文 JSON，文件注释写明"等有真正的后端时再做加密"。现在就是这个时机：refresh token 存进 macOS 钥匙串 / Windows 凭据管理器。

有一个实现上的约束：模型调用发生在 Runtime Host 进程里，而 Electron 的 `safeStorage` 只能在主进程使用。所以由主进程负责登录和保管 refresh token，按需把短期的 access token 交给 Host；Host 在令牌快过期时向主进程要新的。

### 4.4 组织模型

保持最小：只有 `users`，用户上的 `org_role` 分 `member` / `org_admin` 两级。不设团队：额度按人设，模型对全员开放（停用即对所有人下线），用量按人统计；按部门分组、分预算等需求真出现时再加。

## 5. 模型与搜索网关（阶段 1）

### 5.1 形态（D3）

按协议分路径的透明代理。对 Maka 暴露三类原生协议，每类背后可以配置多个上游提供方：

| 对 Maka 暴露的接口 | 可配置的上游 |
|---|---|
| `POST /model/anthropic/v1/messages` | Anthropic API、AWS Bedrock、Google Vertex AI |
| `POST /model/openai/v1/chat/completions`、`/v1/responses` | OpenAI、Azure OpenAI、任何 OpenAI 兼容服务（vLLM 等自部署模型，或其他厂商） |
| `POST /model/gemini/...` | Gemini API、Google Vertex AI |
| `GET /model/catalog` | 当前用户可用的模型 |
| `POST /tools/web-search` | 公司采购的搜索服务（如 Tavily），由网关持有 key |

同一家模型在不同上游，鉴权方式、请求地址和流式编码都不一样（例如 Bedrock 的流式响应不是 SSE）。这些差异由网关内的上游适配器抹平，Maka 看到的始终是原生协议。

**模型路由表**由管理员配置：对用户展示的模型 id → 协议、上游提供方、上游模型名、凭据引用。同一个模型可以配多个上游，用于故障切换。换厂商、换区域只改路由表，Maka 不用动。

**模型目录**（`/model/catalog`）的字段要和 Maka 的模型元数据对齐：上下文长度、支持的思考等级、输入模态、工具调用能力，外加对应的原始模型 id，让 Maka 现有的 models.dev 能力解析照常工作；服务端给出的值优先。

Maka 的所有模型调用都走网关，包括后台调用：记忆整理、会话命名、上下文压缩、定时任务。

每个请求的处理顺序：

1. 验证 access token；
2. 检查模型是否可用：阶段 1 只看模型是否启用（启用即全员可用），阶段 2 起再叠加组织策略（§6）；
3. 额度预检；
4. 换成上游凭据；
5. 流式透传；
6. 从流里解析 usage 并记账。

### 5.2 计量与额度

- **`usage` 表**：用户、模型、输入/输出/缓存写/缓存读 token、加权成本、请求 id、客户端版本、耗时、状态。
- **加权公式**：先沿用 relx 的做法，输入×1、输出×5、缓存写×1.25、缓存读×0.1，再乘模型权重。之后可以改成按真实价格计算。
- **额度**：按人，周期按周或按月；组织设一个默认额度，个别人可以单独设。周额度和月额度都设了时，请求要两者都有余量。超额返回 429 和结构化错误体（并告诉客户端不要重试），Maka 显示成可读提示。
- **额度是软上限**：预检之后并发的请求可能让用量略超一点，第一版接受。
- **中途断开也计费**：员工中途取消时，上游已经产生的 token 仍然计入；流里没拿到 usage 的，按已传输内容估算。
- **审计**：默认只记元数据（D6）。

### 5.3 Maka 侧改动

- 新增一种 provider：组织账号。`authKind` 为组织会话，按模型所属协议路由到网关的对应路径，令牌自动刷新。
- 模型列表直接取 `/model/catalog`。
- 网页搜索改走 `/tools/web-search`。
- 替换现在需要手动填网址的 `relx-gateway` provider（`packages/core/src/provider-registry.ts`）。
- 组织账号下的模型分属 Anthropic、OpenAI、Gemini 三种协议。Maka 已经支持按模型选协议（`ModelInfo.apiProtocol` + provider 的 `protocolAdapters`，`packages/runtime/src/model-runtime.ts`），还需要补两处：协议值里加上 Google；每种协议各有自己的网关地址（现在一个连接只有一个 baseUrl）。
- 模型调用链路已经有按请求注入令牌的钩子（`ModelFactoryInput.fetch`），组织账号的 access token 从这里带上。Host 通过它向主进程调用服务的通道（`client-capability-coordinator` 的 `callService`）向主进程要令牌。
- 保留员工自己添加模型连接的功能（D9）；那部分调用不经过网关，不计入公司额度。
- 结果：员工电脑上不再保存公司的任何模型或搜索 API key。

## 6. 组织策略（阶段 2）

- `GET /policy` 返回针对当前用户合并好的策略，带版本号。Maka 启动时和定期拉取，离线时用缓存。
- **合并规则**：
  - 组织策略是上限；
  - 员工自己的设置只能在策略允许的范围内调整。
- v1 的策略字段：
  - 允许的模型和默认模型
  - 是否允许员工自己添加模型连接，以及允许哪些厂商（D9，默认允许）
  - 权限模式上限，例如禁止"完全放开"
  - 禁用的工具，例如 Computer Use、浏览器
  - MCP 服务器允许列表
  - 网络代理
  - 遥测开关
  - 网关是否保存对话内容（D6）
- **落点**：Maka 已有 `RuntimePolicy`（`packages/core/src/runtime-policy.ts`，保存用户设置）。组织策略作为托管层叠加在它上面，由 Host 执行；界面上显示"由组织管理"，并锁定对应设置。
- **必须说清的一点**：在员工自己电脑上执行的限制，只能防止误用，防不了有意绕过。真正能强制的，只有必须经过服务端的东西：模型、搜索、目录、群聊。

## 7. 技能、插件、连接器目录（阶段 2）

- **包格式**：整个技能目录（`SKILL.md` + 脚本 + 参考文件）打成一个包，带内容哈希。包存对象存储，元数据存 Postgres。插件沿用 Claude plugin 的目录结构：`.claude-plugin/plugin.json` + `skills/` + `.mcp.json`。
- **作用域**：组织。个人技能是否同步到服务端，第一版先不做。
- **发布权限**：技能里的脚本会在员工电脑上执行，等同于公司往每台电脑下发代码。所以只有组织管理员能发布；Maka 安装前校验内容哈希；每次发布进审计日志。
- **Maka 侧**：
  - 作为托管来源接入现有的托管技能机制，锁文件、哈希、"有更新/已修改"判断都已具备；
  - 安装器要支持整目录，目前内置技能只打包单个 `SKILL.md`。
- **连接器**：服务端只下发目录（名称、URL、OAuth 元数据）。MCP 由 Maka 在本机连接，每个人各自完成 OAuth。服务端不代管个人的第三方令牌，从根上避开 relx 的明文存储问题。阶段 3 的群聊凭据是例外，见 §8。

## 8. IM 与共享 agent（阶段 3）

### 8.1 功能范围（D8）

Maka 应用里新增 IM，员工之间、员工和 agent 之间都在这里对话。

- **第一版**：
  - 频道：公开或私有；成员与角色（所有者、管理员、成员）；
  - 私聊：人与人一对一。不做"和 agent 私聊"：一个人单独让 agent 干活，就用自己电脑上的 Maka；
  - 线程：对任意一条消息开线程回复；
  - @提及：@人、@agent、@频道全员；
  - 附件；表情回应；
  - 未读数和已读位置；系统通知（Maka 在后台时也能提醒）；
  - 消息的编辑和删除；消息搜索。
- **以后**：在线状态、语音和视频、手机端和网页端、接入外部 IM、把本机 Maka 的会话分享到频道。

需要说清的一点：第一版只有桌面端。Maka 没开着的时候，员工收不到消息提醒。要覆盖手机端，就得另做移动客户端，或者接入外部 IM，这些都放到以后。

### 8.2 分层

把"消息"和"agent 怎么干活"分开：

- **IM 服务**（服务端）：频道、成员、消息、线程、未读、通知、搜索，以及实时推送。它不知道 agent 怎么执行。
- **共享 agent 运行时**：当有人 @ agent，或在 agent 参与的线程里回复时，IM 服务向运行时发一条指派，内容包括谁、在哪个频道和线程、上下文是什么。运行时在该线程的沙箱里执行，把进度和回复写回线程。

这样分开之后，以后如果要接入钉钉、飞书、Slack，只需要在 IM 服务旁边加一个适配器，把外部消息也转成同样的指派，运行时不用改。relx Tag 设计里的 Surface 抽象，思路正是这个。

### 8.3 数据与实时

借鉴 relx 的 Tag：

- **数据**：
  - `channel → thread → message`，一套部署就是一个组织，不再多一层 workspace；私聊是只有两个成员的特殊频道；
  - 成员与角色；每个作用域一个递增的 `seq`（频道顶层一个，每个线程一个）；
  - 消息内容是内容块（文本、附件、agent 的进度清单）；反应；每人的已读位置。
- **附件**：存对象存储，按频道成员鉴权下载。
- **实时推送**：每个用户一条 WebSocket，所有频道共用；多实例之间用 Redis pub/sub 扇出。重连时带上每个频道的 `last_seq` 补齐缺口，缺口太大就提示客户端重新拉取。Tag 的服务端支持补齐，但网页端没用上，这里要用上。
- **长连接的鉴权**：连接建立时校验 access token；令牌刷新后，客户端在同一条连接上发送新令牌续期。账号被停用时，服务端主动断开该用户的所有连接。
- **搜索**：第一版用 Postgres 全文检索；消息量大了再换专门的搜索引擎。
- **消息保留**：保留期限可以在管理后台按组织和频道设置。
- **谁能看消息**：只有频道成员能看频道消息，私聊只有双方能看。管理员可以管理频道（归档、调整成员），但不能通过管理后台翻看私有频道和私聊的内容。合规检查确实需要导出时，按 D6 同样的规则处理：单独开启、指定人员、全程审计。

### 8.4 Maka 侧

- 侧边栏新增 IM：频道列表、私聊、未读标记。
- 频道和线程视图复用现有的对话渲染组件：agent 的回复和进度，用的就是 Maka 现在展示 agent 工作过程的那一套界面。
- 新消息和 @ 提醒用系统通知。
- IM 的连接走登录后的同一条 WebSocket（§3），和阶段 4 的本地执行体桥共用。

### 8.5 共享 agent

- **引擎**：沙箱里的 Maka Runtime Host，不是 relx 的 Python 循环。每个线程一个会话，一个沙箱（D7），不在 API 进程内。
- **触发**：@agent，或在 agent 参与的线程里回复。"自动插话"放到以后。
- **进度**：会话状态以整状态快照加 `rev` 表示（借鉴 Tag），客户端只接受更大的 `rev`。
- **agent 能用什么**：由组织管理员在管理后台统一定义"agent 可用资源"，包括代码仓库（用只读或受限的部署令牌）、连接器、技能、网络白名单。频道管理员只能从这个清单里为自己的频道挑选，并设定 agent 的说明（system prompt）。普通员工拿不到这些凭据本身。
- **身份与权限**，吸取 Tag 的教训（Tag 以 Y 自己的账号执行、没有审批、网络白名单只写在文档里）：
  - agent 以"频道服务身份"执行，不借用任何员工的账号；
  - 它能用的凭据只来自上面的清单，用信封加密保存（§10），执行时以短期令牌的形式临时注入沙箱，不写进镜像或工作目录；
  - 敏感操作在线程里弹出审批卡片，由提问者或频道管理员批准；
  - 沙箱的网络出口按频道配置白名单，并且要真正执行（E2B 支持"全部拒绝 + 显式放行"，运行中也能更新）。平台自己的网关地址始终在白名单里，模型调用走网关；
  - 模型调用同样走网关，用量记在该频道名下。
- **主要工作量**：把 Runtime Host 改造成可以无头运行、多会话、按会话隔离的形态。它现在按客户端发凭据，是单用户的。

### 8.6 沙箱接口与 E2B（D7）

平台通过一个沙箱接口管理共享 agent 的执行环境：创建、暂停、恢复、销毁、更新网络规则、注入凭据、读写工作目录。默认实现是 E2B：

- **沙箱和平台怎么通信**：沙箱里除了 Runtime Host，还有一个小的桥接进程。它主动向平台建立一条长连接（沙箱不对外开放任何端口），用一个只属于这个沙箱、短期有效的令牌认证；平台通过这条连接下发指派，桥接进程在沙箱内部用 Runtime Host 现有的协议转交给引擎，再把进度和回复传回平台。
- **平台必须能被 E2B 访问**：E2B 云里的沙箱要连平台的这条长连接和模型网关，所以这两个入口必须能从公网访问（仍然全部要求认证）。平台如果只部署在内网，就要改用 E2B BYOC，或自建沙箱。员工在公司外用 Maka 本来也需要公网可访问，所以对 RELX 不是额外的要求。
- **E2B 的 API key**：只由平台保管，用于创建和管理沙箱，不进入任何沙箱。

- **镜像**：用 E2B 的自定义模板，把 Maka Runtime Host 和常用工具打进镜像，并设为启动命令。沙箱一创建，引擎就已经在运行。
- **生命周期**：一个线程对应一个沙箱。一轮对话结束、空闲一段时间后暂停，E2B 会保存文件和内存状态，暂停期间不按算力计费；再有人 @ 时恢复，大约 1 秒。线程归档后销毁沙箱。暂停的沙箱不会自动过期，所以归档和定期清理由平台负责。
- **运行时长**：E2B 单次连续运行有上限（Pro 版 24 小时），每次暂停恢复后重新计时。单个任务超过这个时长的，要拆成多轮。
- **隔离**：Firecracker 微虚拟机，每个沙箱有自己的内核，隔离比容器更强。
- **部署方式**：

  | 方式 | 数据在哪 | 适合谁 |
  |---|---|---|
  | E2B 云 | 沙箱里的代码、文件和注入的凭据都在 E2B 的云上 | 可以接受第三方处理这些数据的组织，最省事 |
  | E2B BYOC | 在自己的 AWS 或 GCP 账号里，敏感数据不经过 E2B 云 | 有数据管控要求、用 AWS 或 GCP 的组织，需要和 E2B 签企业合同 |
  | 自建 Kubernetes + gVisor | 完全在自己的环境里 | 用 Azure 或内网、不能用 E2B 的组织；平台提供这个实现作为替代 |

  RELX 用 E2B 云。

  E2B 的基础设施代码开源，也可以完全自托管，但它依赖 Terraform + Nomad、裸金属或嵌套虚拟化的机器，资源要求高（例如 GCP 上至少 24 个 CPU、2.5 TB SSD）。500 人的规模不值得，不作为推荐方式。

Maka 桌面端现有的外部 IM 机器人（飞书、钉钉、企业微信等）保留，它们是"个人助理"：消息进到某个人自己的 Maka，在他本机执行，和这里群聊中的共享 agent 互不影响。

## 9. 本地执行体桥（阶段 4）

- 群聊里的 agent 可以把"需要在某人电脑上做的事"派给那个人在线的 Maka。
- 请求走 Maka 登录后的长连接下发。Maka 把它当作一个普通会话执行，必须由电脑主人本人确认，别人无权替他批准；结果回到原来的线程。

## 10. 安全与运维

**安全**

- 所有令牌和密钥使用信封加密，主密钥放在密钥管理服务里（§3.1）；服务自身的配置密钥从部署环境注入，不写进镜像。
- 审计日志覆盖：登录、令牌吊销、账号停用、策略变更、路由表变更、目录发布、所有管理员操作。
- 服务账号按最小权限配置；按用户限流。
- 客户端 IP（审计、限流用）只在配置了 `MAKA_TRUST_PROXY`（跳数或地址/CIDR）时才采信 `X-Forwarded-For`，默认直接取对端地址。
- 登录残留（过期的登录事务、授权码、refresh token）每小时清理，过期后保留一天以便识别重放。授权码被重复兑换时，吊销它换出的会话。
- 调用身份源的请求有 10 秒超时；网关调用上游时连接设置全部显式传入，并在进程启动时清掉 SDK 会自行读取的 `ANTHROPIC_*` 环境变量。
- 从阶段 1 开始就带自动化安全测试：冒充、state 校验、令牌复用、越权访问。

**运维**

- **接口版本**：平台接口带版本号。服务端至少兼容当前和上一个桌面端版本；版本太旧的客户端收到明确的"请升级"提示，而不是莫名其妙地报错。桌面端装在每个人电脑上，升级节奏不受我们控制，这一点必须从第一天就有。
- **数据库**：迁移脚本随版本发布，只做向前兼容的变更；每日备份，定期演练恢复。
- **可观测性**：OpenTelemetry 的日志、指标、链路追踪；健康检查接口；网关上的上游错误率和延迟单独监控。
- **可用性**：员工用组织账号时，所有模型调用都经过服务端，服务端一停，大家都用不了模型。所以 API 至少两个实例，数据库用带自动故障切换的托管 Postgres；服务端不可用时，Maka 给出明确提示，自带 key 的连接（D9）不受影响。

## 11. 路线

| 阶段 | 内容 | 相对规模 | 完成后得到什么 |
|---|---|---|---|
| 1 | 身份与组织、桌面端登录、模型与搜索网关、Maka 组织账号 provider、管理后台（基础） | 中 | Maka 可以在公司内发布：登录即用，不需要任何 key，统一计量；管理员在网页上管人、管模型、看用量 |
| 2 | 组织策略、技能/插件/连接器目录、管理后台增加对应页面 | 中 | IT 能管底线，技能统一分发 |
| 3 | Maka 应用内的 IM（频道、私聊、线程、通知）+ 共享 agent 运行时 | 大 | 员工在 Maka 里群聊，@agent 就能在线程里干活，类似 Claude Tag |
| 4 | 本地执行体桥 | 中 | 群聊里的 agent 能调动个人电脑 |

阶段 1 是其他所有阶段的前提，建议先只做它，做完再定阶段 2 的细节。

## 12. 还需要业务方确认的问题

技术上的选择都已定下（§0）。下面这些只能由业务方回答，不影响第 1 阶段开工：

1. **问 RELX IT 两件事**：RELX SSO 返回的邮箱是否一定是真实、已验证的公司邮箱（按邮箱认人的安全性建立在这一点上）；Y 的 RELX SSO 应用能否再登记一个回调地址（§4.1）。另外需要一份允许登录的公司邮箱域名清单。
2. **频道里的 agent 主要干什么活**。它在服务器上工作，碰不到员工电脑上的文件，只能用管理员给它的资源（§8.5）。第一批要给它哪些资源，例如哪些代码仓库、哪些内部系统，决定了阶段 3 的价值。
3. **手机上收 IM 消息有多重要**。第一版 IM 只有桌面端（§8.1）；如果很重要，阶段 3 就要把手机端或外部 IM 接入一起规划。
